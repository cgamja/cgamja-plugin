# cgamja 철학 — 바뀌지 않는 것

이 문서는 플러그인의 **고정점**이다. 스킬·템플릿·ADR은 이 문서를 근거로 바뀌고, 이 문서는 사용자(kangr)가 직접 고칠 때만 바뀐다. 어떤 변경이 아래 원칙과 충돌하면 변경이 틀린 것이다. 2026-08-22.

## 1. 무엇인가

**프론트엔드 개발을 "제대로" 하게 만드는 절차 스킬이다.** compound-engineering, agent-skills, OpenSpec처럼 — 코드를 *대신* 짜는 도구가 아니라, 에이전트가 코드를 짤 때 **스펙 → 테스트 → 증거 → 리뷰**를 건너뛰지 못하게 하고, 내가 정한 기준(디자인 원천, 접근성, 플랫폼 적합성, 계약, 테스트 무결성)을 매 작업에 적용하는 것.

대상 프로젝트는 **주어지는 것**이다. greenfield든 brownfield든, React든 Vue든 Svelte든, 이미 Jest를 쓰든 Vitest를 쓰든 — 플러그인은 그 프로젝트의 스택·구조·도구를 **읽고 맞춘다**. 스택을 정하거나 바꾸라고 하지 않는다.

## 2. 무엇이 아닌가

- **보일러플레이트 생성기가 아니다.** 스택을 고르게 하고 템플릿을 찍어내는 것은 목적이 아니다. 세팅은 "이 프로젝트에서 기준을 강제할 수단이 없을 때 최소한으로 붙이는 것"이지 새 프로젝트를 만드는 일이 아니다.
- **특정 스택의 베스트 프랙티스 모음이 아니다.** React/Next/Expo 지식은 *참고 자료*로 있을 수 있지만 절차의 전제가 되면 안 된다. 절차 문서에 프레임워크 이름이 조건으로 나오면 잘못 놓인 것이다.
- **greenfield 전용이 아니다.** 기존 코드·기존 테스트·기존 린트가 있는 프로젝트에서 *그대로* 돌아가야 한다. 기존 것을 걷어내고 우리 것으로 바꾸자고 하지 않는다.
- **품질을 에이전트의 성실함에 기대지 않는다.** "주의 깊게 하라"는 지시는 규칙이 아니다. 규칙은 린트·훅·테스트·CI처럼 **기계가 판정**하는 것만 인정한다.

## 3. 불변 원칙 — 스택과 무관하게 항상

| # | 원칙 | 뜻 |
|---|---|---|
| P1 | **스펙이 먼저** | 행동은 `#### Scenario`(관찰 가능한 WHEN/THEN)로 먼저 적고, 그것이 테스트·스크린샷과 1:1이다. 스펙 없는 구현은 Tier-1(한 줄짜리) 말고는 없다 |
| P2 | **테스트는 게이트** | 실패하는 테스트를 먼저 쓰고 **사람이 승인**한 뒤 구현한다. 구현 턴에 테스트 파일은 읽기전용. 초록을 만들기 위해 assertion을 고치는 건 거부한다 |
| P3 | **증거 없이 완료 없음** | "됐다"는 말이 아니라 `verify` 출력·테스트 결과·뷰포트별 스크린샷·axe 결과가 완료다. 모델은 렌더를 못 보므로 UI는 스크린샷이 필수 |
| P4 | **디자인 원천 존중** | Figma(또는 내가 지정한 원천)가 있으면 그것이 진실이고 코드는 거울이다. 토큰 밖의 색·간격·임의값은 금지. 디자인이 없으면 후보 → 확정 → 구현의 갭 루프로 간다 |
| P5 | **접근성은 기본값** | 네이티브 요소·이름·포커스·대비·터치 타깃·모션은 선택 사항이 아니다. 린트(1층) → axe(2층) → 리뷰 렌즈(3층)로 매번 본다 |
| P6 | **플랫폼 적합성** | 작업 대상이 데스크톱 웹인지 모바일 웹인지 네이티브인지에 따라 증거(뷰포트·안전영역·키보드·hover)가 다르다. 프로필은 프로젝트가 선언하고 리뷰가 대조한다 |
| P7 | **계약은 한 곳, 코드는 생성물만** | API 타입·클라이언트를 손으로 쓰지 않는다. 원천 파일(OpenAPI든 무엇이든) 하나에서 생성하고, 없는 엔드포인트·필드는 코드가 아니라 원천 diff로 제안한다 |
| P8 | **경계는 기계가 막는다** | 도메인 간 import·중복 컴포넌트·상태 이중화 같은 구조 규칙은 산문이 아니라 린트로. 막히면 우회하지 말고 묻는다 |
| P9 | **리뷰는 렌즈, 스타일은 없음** | 정확성·스펙 완전성·테스트 무결성·접근성·플랫폼·계약·성능의 질문을 새 컨텍스트가 던진다. 취향·포맷 지적은 어떤 렌즈에도 없다 |
| P10 | **작게, 자주, 되돌릴 수 있게** | 티어로 규모를 먼저 판정하고, 단위마다 커밋하며, 테스트 커밋과 구현 커밋을 분리한다 |

## 4. 프로젝트를 대하는 방식 — 정하지 말고 발견하라

1. **읽는다**: 패키지 매니저, 프레임워크, 테스트 러너, 린터, 라우터, 스타일 방식, 기존 테스트 위치, CI. 이미 있는 건 그대로 쓴다.
2. **대조한다**: P1~P10을 강제할 수단이 이 프로젝트에 있는가? (테스트 파일 보호, 계약 생성, 경계 린트, a11y 린트, 완료 정의 한 곳)
3. **없는 것만 제안한다**: 최소 단위로, 기존 도구 위에(예: 이미 Jest면 Jest에 a11y 매처를 붙이지 Vitest로 바꾸자고 하지 않는다). 붙일 때는 "이게 실제로 막나"를 프로브로 확인한다.
4. **프로젝트가 답을 갖게 한다**: 결정(허용된 도메인 엣지, 플랫폼 프로필, 디자인 원천, 완료 명령)은 프로젝트의 `CLAUDE.md`·`.claude/rules`·ADR에 적힌다. 플러그인은 절차만 갖는다.

## 5. 도구·스택 지식의 자리

- 특정 스택에서 검증한 사실("orval 8은 MSW+faker를 생성한다", "Vitest Browser Mode는 Chromium만")은 `references/`에 **날짜와 함께** 두고, 절차는 그 사실을 *조건부로* 참조한다. 절차에 "orval을 돌려라"가 아니라 "계약 원천에서 생성하라 — React+OpenAPI면 `references/api-contract.md`"로.
- 새 스택·새 도구는 리서치로 결론 내지 않는다. 설치해서 돌려보고, 실패 모드를 적고, 그 뒤에 references에 넣는다.
- 지식이 낡는 것은 정상이다. 주기적으로 드리프트를 점검하고, 틀린 것은 지운다.

## 6. 검증의 철학

스킬 자체도 P3를 따른다. "스킬을 고쳤다"는 `tests/`(결정적) → 트리거 → 행동 eval → 실제 런의 층에서 증거가 있을 때만 완료다. 실제 런은 탐색이고, 발견은 싼 층의 케이스로 내려간다. 비싼 검증 하나로 "됐다"고 하지 않는다.

## 7. 이 문서가 바뀌는 경우

사용자가 직접 고칠 때만. 에이전트는 이 문서를 근거로 인용할 수 있지만 수정 제안은 ADR로 올리고, 이 파일은 건드리지 않는다.
