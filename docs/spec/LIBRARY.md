## Library — 라이브러리 추가 판단 기준

하네스(Claude Code)가 작업 중 새 라이브러리가 필요하다고 판단하는 순간의 규칙. "어떤 라이브러리를 쓸까"가 아니라 **"애초에 추가해도 되는가 → 된다면 무엇을 근거로 고르는가 → 어떻게 기록하는가"**의 3단계다.

막으려는 문제: 하네스는 사람보다 라이브러리를 훨씬 쉽게 추가한다 — "이거 설치하면 됩니다" 한 줄이면 의존성이 하나 늘고, 그 순간부터 번들 크기·보안 취약점·업그레이드 비용·같은 문제를 푸는 라이브러리 중복이 전부 내 것이 된다. 기준 없이 두면 프로젝트마다 스택이 발산한다.

### 0단계 — 스펙에 있으면 통과 (사전 승인 목록)

[WEB-SPEC.md](./WEB-SPEC.md) / [APP-SPEC.md](./APP-SPEC.md)에 이미 있는 라이브러리는 **이미 결정이 끝난 것**이다 — 이유·버린 대안·비용이 스펙에 기록돼 있으므로, 하네스는 추가 검토·ADR 없이 설치를 제안할 수 있다. `@types/*`, 이미 있는 라이브러리의 공식 어댑터/플러그인(예: `@tanstack/react-query-devtools`)도 여기 포함.

스펙에 없는 라이브러리는 전부 아래 게이트를 거친다.

### 1단계 — 추가해도 되는가 (게이트, 순서대로)

하나라도 걸리면 라이브러리를 추가하지 않는다:

1. **문제로 시작하는가** — "어떤 문제를 겪고 있나"를 한 문장으로 못 쓰면 반려. "있으면 편해서", "보통 이걸 써서"는 문제가 아니다 ([PHILOSOPHY.md](./PHILOSOPHY.md) 프레이밍 규칙)
2. **기존 스택으로 안 되는가** — 스펙의 기존 라이브러리·플랫폼 API(fetch, Intl, CSS)로 풀리는 문제면 반려. 특히 **같은 문제를 푸는 라이브러리는 프로젝트에 하나만** — Tanstack Query가 있는데 SWR, Zustand가 있는데 Jotai를 추가하지 않는다 (이름 겹침이 아니라 역할 겹침 금지)
3. **직접 구현이 더 싸지 않은가** — AHA 원칙의 의존성 버전: 잘못된 의존성은 잘못된 추상화처럼 해체 비용이 크다. 판단 기준:
   - 필요한 게 라이브러리 기능의 **일부(감으로 ~10%)뿐**이고, 그 부분이 엣지 케이스가 적은 코드(수십 줄)면 → 직접 구현
   - 엣지 케이스가 본질인 영역(날짜/시간대, 파싱, 접근성 위젯, 암호화, 가상화)이면 → 라이브러리. 직접 구현이 오히려 비싸다

### 2단계 — 무엇을 근거로 고르는가 (후보 검진)

게이트를 통과했으면 후보를 검진하고 **아래 표 형식으로 보고**한다. 형식 없는 "이거 설치할게요"는 반려 — [DOCTOR.md](./DOCTOR.md)의 보고 원칙과 동일하다.

| 항목 | 확인 방법 | 판정 기준 |
| --- | --- | --- |
| 유지보수 | npm 최근 릴리스, GitHub 최근 커밋 | 마지막 릴리스 12개월 이내. 아니면 "완성된 라이브러리"인지(zero-dep 소형 유틸) 별도 소명 |
| 사용 규모 | 주간 다운로드, 의존하는 패키지 수 | 절대 컷 없음 — 같은 문제의 대안 대비 비교. 극소수 다운로드면 사람 승인 필수 |
| 번들 크기 | bundlephobia (gzip, 트리셰이킹 여부) | 크기 자체보다 "푸는 문제 대비 비례하는가". 대안 대비 표기 |
| 전이 의존성 | 설치 시 딸려오는 패키지 수 | 소형 유틸인데 의존성이 줄줄이면 감점 |
| 보안 | `npm audit`, 알려진 CVE | high/critical 있으면 반려 |
| 타입 | TS 내장 or `@types/*` | 없으면 반려 (strict 전제 — WEB-SPEC) |
| 모듈 형식 | ESM, RSC 호환(웹), Expo 호환(앱) | 스펙 스택에서 실제로 동작하는가 |
| 라이선스 | package.json | MIT/Apache-2.0/BSD/ISC는 통과, 그 외(GPL 계열, 미상)는 사람 판단 |

판정 기준에 숫자 컷이 적은 이유: 다운로드 수·크기는 카테고리마다 스케일이 달라 절대값 컷이 오판을 만든다. 원칙은 **"항상 대안과 나란히 비교해서 보고"** — 비교 없는 단독 추천은 반려.

### 3단계 — 어떻게 기록하는가

- 사람이 승인하면 설치하고, **ADR을 쓴다** ([ADR.md](./ADR.md) 트리거 2 "새 라이브러리를 의존성에 추가할 때"). 2단계 보고 내용이 그대로 ADR의 문제→결정→대안→트레이드오프가 된다
- 커밋은 `chore(deps): ...`로 분리 ([COMMIT.md](./COMMIT.md), [DOCTOR.md](./DOCTOR.md) 규칙과 동일)
- 같은 라이브러리가 **프로젝트 2곳 이상에서 채택되고 ADR 근거가 겹치면** 스펙 문서(WEB/APP-SPEC) 승격 후보 — 승격하면 다음부터는 0단계 통과

### 강제 수단 (실행되지 않는 철학은 철학이 아니다)

- **훅**: 프로젝트 세팅(develop-setup)의 `protect-bash` 훅이 패키지 추가 명령(`npm install <pkg>`, `pnpm add`, `expo install` 등)을 차단한다 — 하네스는 단독으로 의존성을 추가할 수 없고, 반드시 위 보고 → 사람 승인 경로를 거친다
- **리뷰**: review-cgamja가 이 문서·WEB/APP-SPEC 대조로 "ADR 없는 의존성 추가"를 반려한다(package.json diff에 승인 흔적이 없으면 blocker). 의존성 **크기**의 자동 검사 게이트는 현재 없다 — 크기·번들 영향은 승인 질문에서 사람이 본다
- **ADR 트리거**: 새 의존성 = ADR 자동 트리거 (기록 없는 추가는 리뷰 반려 사유)
- **doctor**: 추가 이후의 건강(버전·audit)은 [DOCTOR.md](./DOCTOR.md)가 주기적으로 담당
