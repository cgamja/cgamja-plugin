# cgamja 프론트엔드 철학

> 이 레포의 최상위 문서. `docs/` 아래 모든 문서는 이 철학의 구현체다.
> 유파가 충돌하는 지점의 결정은 전부 **내가 정한 것** — 이게 이 철학이 요약본이 아닌 이유다. 실전 사례가 생기면 그 사례를 근거로 덧붙인다.

## 정체성: 실행되지 않는 철학은 철학이 아니다

좋은 코드 원칙은 이미 세상에 많다. 내 철학의 축은 원칙의 발명이 아니라 **원칙을 AI 하네스(Claude Code)가 강제·실행할 수 있는 규칙으로 번역하는 것**이다.

- 사람이 읽는 지침 → 린트 룰, 훅, 워크플로우(doctor), 보고 형식으로 바꾼다
- "강제 수단을 못 만드는 원칙"은 채택하지 않거나, 리뷰 렌즈(체크리스트)로라도 만든다
- 문서는 사람과 AI가 같은 것을 읽는다 — 그래서 모든 규칙은 판단 기준(언제/언제 아닌지)까지 쓴다

이 축은 참고한 어떤 소스에도 없다. 토스 FF는 사람 문화로 강제하고, 나는 도구로 강제한다.

## 프레이밍 규칙: 규칙은 문제에서 나온다

모든 규칙·선택은 **"어떤 문제를 겪었나/막으려 하나"로 시작**해서 기록한다. "토스가 하니까"는 출처지 이유가 아니다.

- Bad: "토스 클린코드 영상을 보고 선언형 설계를 적용했다"
- Good: "비동기 상태(로딩/에러) 분기가 UI 로직과 섞여 읽기 어려워지는 문제가 있어, 선언적 처리로 비즈니스 로직과 렌더링을 분리했다"

적용 형태:
- 스펙 문서(WEB/APP-SPEC): 모든 항목에 이유 + **버린 대안** + **감수한 비용**을 기록 — 비용을 못 적었다면 아직 대안을 충분히 안 본 것
- 프로젝트별 결정: 각 프로젝트 `adr/`에 문제→결정→대안→트레이드오프→재검토 조건 순으로 ([ADR.md](./ADR.md))
- 이 문서의 결정들: 실전 사례가 생기면 그 사례를 근거로 덧붙인다

## 유파가 충돌하는 지점 — 내 결정

### 1. 얼마나 잘게 쪼갤 것인가 (토스 vs Ousterhout)

토스 FF는 "로직 종류별로 함수를 쪼개라"고 하고, Ousterhout는 "작은 모듈은 얕다 — 쪼개기 자체가 복잡도를 늘린다"고 한다.

**내 결정: 토스 우선 — 실행 경로가 다르면 무조건 분리한다** (SubmitButton 예제 방식).

버린 대안: Ousterhout 우선(인터페이스가 단순해질 때만 분리) / 절충안(분리하되 같은 파일 안에서). 하네스(AI)가 코드를 읽고 쓰는 환경에선 한 파일에 여러 실행 경로가 섞이는 비용이 파일 수가 늘어나는 비용보다 크다.

### 2. 4원칙 충돌 시 디폴트 우선순위 (토스는 "정답 없음") 

**내 결정: 예측가능성 > 결합도 > 가독성 > 응집도.**

근거: 하네스(AI)가 코드를 쓰는 환경에선 예측가능성 위반이 가장 비싸다 — AI는 숨은 로직·이름 겹침에 사람보다 더 잘 속고, 한 번 속으면 그 위에 코드를 계속 쌓는다. 결합도가 그다음인 이유는 잘못된 결합이 변경 비용으로 직결되기 때문이고, 가독성·응집도는 리뷰 렌즈로 잡을 수 있는 문제라 뒤에 둔다.

### 3. 추상화 타이밍 (DRY vs AHA)

**내 결정: AHA 진영.** 중복 2회까지 허용, 3회째 + "함께 변경된다"는 확신이 있을 때만 공통화. 잘못된 추상화의 해체 비용 > 중복 유지 비용. 판단 기준은 [GOOD-BAD-PATTERN.md](./GOOD-BAD-PATTERN.md) §6.

### 4. 테스트 투자 배분

**내 결정: Testing Trophy 그대로** (통합 > 단위 > E2E > 정적).

하네스가 테스트를 대량 생산할 수 있는 환경에서 단위/E2E 비중을 조정할지는 실전 경험이 쌓이면 재검토한다.

### 5. 매직 넘버의 위치

**내 결정:** 이름은 무조건, 위치는 사용 범위만큼만: 한 파일 → 파일 상단 / 한 feature → `features/<f>/constants.ts` / 전역(소수) → shared. 전역 constants 덤핑 금지(결합 지점화). 우연히 값만 같은 숫자는 합치지 않는다.

## 앞으로 이 문서를 키우는 법

- 각 결정은 실전 프로젝트에서 부딪힌 사례가 생기면 **결정 이유와 겪은 사례**를 덧붙인다 — 재검토가 필요해지면 이유와 함께 결정을 갱신한다
- [GOOD-BAD-PATTERN.md](./GOOD-BAD-PATTERN.md)의 토스 예제는 내 프로젝트에서 나온 실제 사례로 하나씩 교체한다
- 소스는 계속 추가하되, "취한 것 / 버린 것" 없이 추가하지 않는다 — 요약은 철학이 아니다
- 외부 비판(면접 피드백 등)을 받으면 수용/반박을 이 문서에 기록한다 — 2026-08: "토스 요약본" 비판을 수용해 프레이밍 규칙·ADR·트레이드오프 기록을 도입, "문서-코드 괴리" 비판은 하네스 강제 축으로 반박
