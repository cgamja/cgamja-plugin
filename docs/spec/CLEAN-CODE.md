## Clean Code

> 기반: 토스 Frontend Fundamentals — "좋은 코드는 **변경하기 쉬운 코드**다."
> 네 기준(가독성 · 예측 가능성 · 응집도 · 결합도)이 서로 충돌하면, **지금 이 코드가 어떤 변경을 자주 겪는지**를 기준으로 우선순위를 정한다. 정답은 하나가 아니다.

### 1. 가독성 (Readability)

**맥락 줄이기**
- 같이 실행되지 않는 코드는 분리한다 (예: 권한별 분기가 섞인 컴포넌트 → 역할별 컴포넌트로 쪼갠다)
- 구현 상세는 추상화한다 — 읽는 사람이 한 번에 고려할 맥락은 6~7개 이내
- 로직 종류(상태, 이벤트, 렌더링)가 섞인 함수/훅은 종류별로 쪼갠다

**이름 붙이기**
- 복잡한 조건식에는 이름을 붙인다 (`const isSameCategory = ...`)
- 매직 넘버에는 이름을 붙인다 (`const ANIMATION_DELAY_MS = 300`)

**위에서 아래로 읽히게 하기**
- 시점 이동(파일/함수 사이 왔다 갔다)을 줄인다
- 삼항 연산자는 중첩하지 않는다 — 복잡해지면 `if`나 변수로 푼다
- 왼쪽에서 오른쪽, 위에서 아래로 읽히게 쓴다

### 2. 예측 가능성 (Predictability)

- 이름이 겹치지 않게 관리한다 — 같은 이름이면 같은 동작을 해야 한다 (라이브러리 함수를 감싼 함수에 원본과 같은 이름을 쓰면서 동작을 바꾸지 않는다)
- 같은 종류의 함수/훅은 반환 타입을 통일한다 (예: validation 함수는 항상 `{ ok: true } | { ok: false; reason: string }`)
- 숨은 로직을 드러낸다 — 함수 이름·파라미터·반환 타입에 드러나지 않는 부수효과(로깅, 캐시 갱신 등)를 몰래 넣지 않는다

### 3. 응집도 (Cohesion)

- 함께 수정되는 파일은 같은 디렉토리에 둔다 (도메인 기준 구조 > 종류 기준 구조)
- 매직 넘버를 상수로 모아 수정 지점을 하나로 만든다 — 위치는 사용 범위만큼만 넓게(한 파일이면 파일 상단, feature면 `constants.ts`, 전역 덤핑 금지). 우연히 값만 같은 숫자는 합치지 않는다 ([PHILOSOPHY.md](./PHILOSOPHY.md) 결정 5)
- 폼 응집도는 의도적으로 선택한다 — 필드 단위(독립 검증·재사용) vs 폼 단위(하나의 비즈니스 단위)를 상황에 맞게

### 4. 결합도 (Coupling)

- 책임은 하나씩 관리한다 — 쿼리 파라미터 전체를 다루는 만능 훅보다, 파라미터 하나씩 다루는 훅
- **성급한 추상화보다 중복을 허용한다** — 페이지마다 동작이 달라질 여지가 있다면 공통화하지 않는 편이 변경에 안전하다
- Props Drilling은 결합의 신호 — 조합(children) 패턴이나 컨텍스트로 지운다

### 선언적으로 쓰기 (SLASH 21 — 실무에서 바로 쓰는 Frontend Clean Code)

- **뭉치기**: "당장 몰라도 되는 디테일"은 함수/컴포넌트로 숨기고 핵심만 드러낸다 (`openPopupToNotAgreedUsers()`)
- **단일책임**: 함수 이름이 하는 일을 완전히 표현할 것 — 여러 역할이면 쪼갠다 (`handleQuestionSubmit` → `handleNewExpertQuestionSubmit` / `handleMyExpertQuestionSubmit`)
- **추상화 수준 통일**: 한 함수/컴포넌트 안에서 고수준 개념과 저수준 구현이 섞이지 않게 한다
- 비동기 자원은 React Query 등으로 선언적으로 관리한다 (로딩·에러 분기를 명령형으로 흩뿌리지 않는다)

### 이름 규칙

- 컴포넌트: **PascalCase**
- 함수/변수: camelCase, 상수: UPPER_SNAKE_CASE
- 불리언은 `is/has/can/should` 접두사
- 이름은 "무엇을 하는지"가 아니라 "왜 존재하는지"까지 담기게

### 주석 (토스 스타일)

- 주석은 **코드로 표현할 수 없는 것만** 쓴다: "무엇"이 아니라 **"왜"와 맥락**
- 코드를 요약·중계하는 주석은 금지 — 그런 주석이 필요하면 코드(이름·구조)를 고친다
- 좋은 주석의 예: 우회 코드를 쓴 이유, 외부 제약(브라우저 버그, API 스펙), 의도적으로 하지 않은 것
- JSDoc은 공용 유틸/훅의 계약(파라미터·반환·예외)을 설명할 때만
