## ADR 후보

### 0028 — 훅의 "명령 대상" 판정을 경로 해석으로 (adr/0017·0023 보강)
근거: 위 §A 오탐 4건 전부가 **문자열 매칭**에서 나온다 — heredoc 본문의 파일명, `2>&1` 의 `2>`, 프로젝트 밖 경로. 오탐이 4회차로 누적됐고 세 번의 정밀화(0017·0023)로도 계열이 남았다. 문자열이 아니라 (a) cwd 기준 경로 해석 (b) 리다이렉트 fd 토큰 분리 (c) 프로젝트 루트 밖 경로는 대상에서 제외 로 바꾼다.
고칠 파일: `skills/develop-setup/templates/hooks/protect-bash.sh`, `_lib.sh`

### 0029 — bypassPermissions 세션의 red 게이트 처리를 세션 시작에서 판정
근거: §B. 게이트 무력화를 첫 테스트 Edit 직전에야 발견해 되물음 2회 + 부정확한 안내가 발생했다. `workflow.md` 0장에서 `permission_mode` 를 읽어 **티어 판정과 함께** 한 줄로 알리고, Tier-2 면 그 자리에서 대체 증거(실패 출력 원문 보고) 합의를 받는다.
고칠 파일: `skills/develop-fe/workflow.md` 0장, `SKILL.md` 시작 절차

### 0030 — 가드는 "되돌리면 실패하는가"를 통과 조건에 넣는다
근거: §C 3~4건. 전부 "초록을 보고 통과라고 믿은 것"이다. 자체 프로브·새로 만든 테스트는 **의도적으로 깨서 빨강을 확인**해야 완료로 친다. develop-setup 의 smoke 는 이미 이 원칙을 갖고 있는데(`조용히 통과는 설정 문제`) develop-fe 의 task `verify:` 에는 없다.
고칠 파일: `skills/develop-fe/workflow.md` 3장, OpenSpec `feature` 스키마의 tasks instruction

### 0031 — change당 커밋 수 상한과 `[develop-fe]` 넛지의 강제력
근거: 조건 발동(11·16개). 다만 원인이 "규칙 위반"이 아니라 **리뷰 라운드마다 test/fix 를 분리 커밋**한 것이라, 상한을 낮추는 게 아니라 조건 문구를 "리뷰 수정 커밋 제외"로 고치는 쪽이 맞는지 판단이 필요하다. 함께: advisory 넛지가 무시된 사례(§A) — 리뷰 목적 Agent 는 차단하되 **분석·탐색 목적 Agent 는 통과**시켜야 한다(이번 회고의 트랜스크립트 분석 Agent 에도 오발동).
고칠 파일: `skills/develop-fe/workflow.md` 7장, `skills/develop-fe/hooks/skill_guard.sh`

## 사용자가 회고 중에 준 코드 기준 3건 (반영 완료)

트랜스크립트 집계가 아니라 사용자가 직접 지적한 것이다. 셋 다 **이 세션의 산출물이 실제로 어기고 있었다**.

| 지적 | 세션 코드의 상태 | 반영 |
|---|---|---|
| 상수는 도메인별로 모아 의미 있는 이름으로 꺼내 쓴다. 타입·상수·상태를 코드 파일에 다 정의하니 지저분하다 | `WaitlistSignupForm.tsx` 가 타입(`Status`)·상수(`INITIAL`·`VALIDATION_MESSAGE`)·상태·렌더를 한 파일에서 다 함 | `model/types.ts` · `model/constants.ts` 분리, 로직 파일은 가져다 쓰기만 |
| 문장은 상수로 빼서 관리(유지보수) | JSX 안에 한글 문장 **8개** 흩어짐 | `ui/messages.ts` 한 곳으로. 폼의 인라인 문장 0 |
| Props 를 잘 생각(철학·의미에 따라 Context 등, 성능 우선) | 폼이 props 를 안 받아 당장 위반은 없음 | 판단 **기준**이 없던 게 문제 — `CLEAN-CODE.md` 결합도 절에 3단계(조합→의미상 주변 환경→성능) 추가 |

문서 반영: 플러그인 `docs/spec/CLEAN-CODE.md`(응집도·결합도), 프로젝트 `.claude/rules/components.md`.
검증: 43 passed 유지(동작 변화 없음), 폼 121줄.

> **테스트는 문장 리터럴을 그대로 둔다.** `messages.ts` 를 import 하면 카피를 바꿔도 테스트가 통과해 버린다 — 사용자에게 보이는 말이 바뀌면 테스트가 깨져서 알아채는 게 맞다.

### 이 3건이 리뷰 2축에 안 걸린 이유

`review-cgamja` 는 `docs/spec/` 대조인데 **그 문서에 이 규칙이 없었다**(매직 넘버 상수화만 있고 문장·타입 배치·Props 판단 기준은 없음). 리뷰어는 문서에 없는 것을 위반으로 판정하지 않는다 — 설계대로 동작한 것이고, 공백은 문서 쪽이었다. 실제로 철학 축은 이번 change 를 PASS 로 판정했다.
→ **재검토 조건 후보**: "리뷰 2축이 PASS 했는데 사용자가 코드 기준을 지적 2회 → `docs/spec/` 커버리지 점검".
