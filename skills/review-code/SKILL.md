# review-code — 철학 + 정확성 리뷰 게이트

두 축을 나눠 본다. **철학 리뷰**는 "문서에 적힌 규칙과 어긋나는가"만 판정하고(취향 금지), **정확성 리뷰**는 "이 코드가 틀린 입력·상태에서 깨지는가"를 본다. 둘 다 새 컨텍스트의 에이전트가 해야 한다 — 작성자가 자기 코드를 보면 의도를 알아서 빈틈을 못 본다.

## 1. 범위와 근거 문서

- 범위: 사용자가 지정한 것 > `git diff <base>..HEAD`(브랜치 작업이면 base는 `origin/main`) > `git diff HEAD`(스테이징 포함 변경분) > 직전 커밋. 비어 있으면 무엇을 볼지 묻고 멈춘다.
- 철학 문서 루트: 프로젝트 `CLAUDE.md`가 가리키는 곳(예: `~/cgamja-philosophy/docs/`)이 우선, 없으면 cgamja 플러그인의 `docs/spec/`. **절대 경로**로 에이전트에 넘긴다.
- 프로젝트 규칙: `CLAUDE.md`와 `adr/`를 같이 넘긴다. 프로젝트 ADR이 철학 문서의 기본값을 바꿨을 수 있다(예: 움직임 범위).
- 웹인지 앱(RN)인지 — WEB-SPEC/APP-SPEC 선택용.

## 2. 에이전트 스폰 (한 메시지에)

- 철학: `cgamja:reviewer-cgamja`. 프롬프트에 범위(커밋 해시·diff 명령), 문서 루트, CLAUDE.md·adr 경로, 특히 봐 줄 것(새 모듈·서버/클라이언트 경계·중복 vs 추상화·접근성·커밋 메시지)을 넣는다. 출력 형식은 에이전트가 안다(PASS/FAIL·위반마다 파일:줄·조항 인용·제안·잘 지킨 것·문서에 규칙 없는 영역).
- 정확성(기본 켬, `--no-correctness`로 끔): `cgamja-private:code-review-opus`가 있으면 그것(세션 모델과 무관하게 Opus — Fable 세션에서 `/code-review`는 fork라 같은 모델이 자기 코드를 본다). 없으면 `cgamja:reviewer-correctness`. 범위와 "확인된 버그·회귀만, 취향 금지, 파일:줄과 재현 시나리오"를 넣는다.
- 둘 다 읽기 전용이다. 고치는 건 3단계에서 내가 한다.

기다리는 동안 다른 독립 작업(빌드·스크린샷)을 진행한다. 결과를 예측해서 먼저 고치지 않는다.

## 3. 판정 처리

- 철학 **blocker/should**: 제안대로 고친다. 제안이 틀렸다고 보이면 고치지 말고 이유와 함께 사용자에게. **info**는 고치면 좋은 것 — 비용이 작으면 같이 한다.
- 정확성 **confirmed**: 고치고 재현 케이스를 테스트로 남긴다. **plausible**은 사용자에게 판단을 넘긴다.
- **문서에 규칙이 없는 영역**: 고치지 않는다. 철학 문서에 넣을지는 사용자 결정(PHILOSOPHY의 성장 규칙). 목록으로 전달.
- 자주 나오는 should와 방향:
  - 시간·간격·크기 매직 넘버 → 파일 상단에 이름(`AFTER_TITLE_S`). 우연히 같은 값은 합치지 않는다.
  - reduced-motion/권한/상태 분기가 삼항으로 한 컴포넌트에 섞임 → 얼리 리턴으로 경로 분리.
  - 물건 하나에만 쓰는 상수가 shared 모듈에 → 그 물건 옆 data 모듈로(서버/클라이언트 경계가 이유면 주석에 적는다).
  - 코드 요약 주석(`{/* 몸통 */}`) → 이름 있는 하위 컴포넌트로.
  - `"use client"` 모듈의 비컴포넌트 export를 서버가 호출 → 값이 아니라 참조가 되어 빌드가 깨진다. 평범한 `.ts` 데이터 모듈로 분리.
- 고친 뒤 **철학 재검사 1회**만. 두 번째도 FAIL이면 멈추고 남은 것을 사용자에게 — 무한 루프 금지. 판정을 통과시키려고 철학 문서를 고치지 않는다.
- 프로젝트 검증 명령(`pnpm verify`·테스트)을 마지막에 한 번.

## 4. 커밋 (COMMIT.md)

- 제목 50자 이내·명사형 종결·Conventional type. 커밋 하나 = 의도 하나(리뷰 반영은 `fix(review)`나 `refactor`로 따로).
- 파일이 겹쳐 의도별로 못 나누면, 나눈 커밋이 각각 빌드되는지 먼저 따져 보고 안 되면 한 커밋에 두되 본문에 사유를 적는다. 리뷰어가 커밋 메시지 위반을 짚었는데 이미 푸시된 커밋이면 고치지 않고 PR에서 스쿼시를 권한다.

## 5. 보고

에이전트 보고를 붙여 넣지 말고 요약한다: 판정 · 위반 n건 중 m건 수정 · 남은 것과 이유 · 문서에 규칙이 없는 영역 · 정확성 확인/추정 건수. 같은 위반이 반복됐으면 "GOOD-BAD-PATTERN.md에 사례로 추가할까?"를 제안한다 — 실전 사례로 예제를 교체하는 것이 이 철학의 성장 방식이다.

## 주의

- 철학 리뷰에 취향을 섞지 않는다. 문서에 없으면 "규칙 없는 영역"이지 위반이 아니다.
- 정확성 리뷰어가 "확인됨"이라 해도 재현이 안 되면 사용자에게 그렇게 말한다.
- SEO·성능·접근성 감사는 이 스킬이 아니다 → `review-seo`. 둘 다면 `review-cgamja`.
