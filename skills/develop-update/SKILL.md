# develop-update

플러그인은 심링크라 고치면 즉시 반영된다. **그런데 훅·rules·settings 는 대상 레포로 복사된다** — 플러그인을 고쳐도 따라오지 않는다. 이 스킬이 그 간극을 닫는다.

`develop-setup` 이 "처음 한 번"이라면 이 스킬은 "그 뒤 계속"이다. 스택을 발견하지도, 도구를 고르지도 않는다 — **이미 정해진 것을 현재 버전으로 맞추기만 한다.**

## 이 스킬이 존재하는 이유 (2026-09-01 실측)

`~/app` 은 2026-08-22 버전 훅으로 10일을 돌았다. 그 사이 플러그인에서 고쳐진 오탐 4계열과 우회 3종이 전부 빠져 있었고, `red-mark.sh`(adr/0018 red 게이트)는 **파일 자체가 없었다.** 아무도 몰랐다.

adr/0023 이 이걸 대비해 버전 마커(`# cgamja-hooks v<N>`)와 드리프트 감지를 뒀지만 **울리지 않았다** — 마커를 손으로 올려야 하는데 그날 세 번의 수정에서 아무도 안 올렸다. 산문 규칙은 지켜지지 않는다(adr/0031). 그래서 이 스킬은 **정수 마커를 신뢰하지 않고 내용을 대조한다.**

## 0. 전제 확인 — 이 스킬의 대상인가
`.claude/cgamja.json` 이 없으면 **update 가 아니라 setup 이다.** 훅은 선언에서 패턴을 읽으므로(adr/0014) 선언이 없으면 훅이 아무것도 보호하지 않는다 — 파일만 새것으로 덮으면 "최신인데 아무것도 안 막는" 상태가 된다. `/develop-setup` 으로 보내고 멈춘다.

## 1. 대조 — `bash scripts/drift.sh <dir>`
정수 마커가 아니라 **내용**으로 본다. 네 축을 각각 `같음 / 다름 / 없음(신규)` 으로 낸다.

| 축 | 대조 대상 | "다름"의 의미 |
|---|---|---|
| 훅 스크립트 | `.claude/hooks/*.sh` ↔ `templates/hooks/` | 오탐·우회 수정이 안 들어왔다 |
| 훅 등록 | `.claude/settings.json` 의 `command:` 목록 ↔ 템플릿의 훅 목록 | 파일은 있는데 **불리지 않는다** — 가장 조용한 실패다 |
| 선언 슬롯 | `cgamja.json` 의 키 ↔ `templates/cgamja.json` 의 키 | 새 강제 수단이 읽을 자리가 없다 |
| rules | `.claude/rules/*.md` 의 구조(`[강제 수단]` 표기 등) ↔ 템플릿 | 규칙이 산문으로만 남아 있다 |

**훅 파일 내용은 템플릿과 1바이트도 다르면 안 된다** — 훅은 프로젝트 고유값을 선언에서 읽으므로 손댈 이유가 없다. 다르면 그건 갱신 누락이거나 누군가 훅을 고친 것이고, 후자면 그 수정은 플러그인으로 올라가야 한다(프로젝트에 남기지 않는다).

## 2. 적용 — 무엇을 덮고 무엇을 보존하는가
| | 처리 |
|---|---|
| `.claude/hooks/*.sh` | **템플릿 그대로 덮어쓴다.** 신규 훅은 복사 + `settings.json` 에 등록까지 해야 끝이다 |
| `.claude/settings.json` | `hooks`·`permissions.deny` 에 **없는 것만 추가.** 프로젝트가 추가한 항목·`enabledPlugins`·env 는 건드리지 않는다 |
| `.claude/cgamja.json` | **없는 키만 추가**하고 값은 `null` 로 둔다 — 값을 정하는 건 setup 의 일이다. 기존 값은 절대 덮지 않는다(`protected` 목록·`lint_file.command` 는 프로젝트마다 다르다) |
| `.claude/rules/*.md` | 자동으로 덮지 않는다 — 내용이 프로젝트 고유다. **구조 격차만 보고**하고 고치는 건 사람·후속 커밋 |

## 3. ADR 반영 확인
프로젝트의 마지막 갱신 이후 플러그인에 추가된 ADR 중 **프로젝트 산출물을 요구하는 것**을 목록으로 낸다(`adr/README.md` 목록 ↔ 프로젝트의 훅·선언·rules). 예: adr/0018 은 `red-mark.sh` + 등록을, adr/0030 은 `parallel` 선언을, adr/0031 은 rules 의 `[강제 수단]` 표기를 요구한다. **자동 반영하지 않는다** — 무엇이 빠졌는지 보이게 하는 것이 목적이다.

## 4. 검증 — 갱신했다가 아니라 작동한다
1. `bash <develop-setup>/scripts/hook-cases.sh <dir>` — 훅이 진짜 막고 진짜 통과시키는가. **전부 초록이어야 한다.**
2. `bash <develop-setup>/scripts/smoke.sh check <dir>` — 세팅 전체. ✗ 가 남으면 그건 update 가 아니라 setup 격차다(§5 로 보고).

프로브가 ✗ 를 내면 **갱신을 되돌리지 말고** 원인을 보고한다 — 새 검사가 기존 격차를 처음 비춘 것일 때가 많다(2026-09-01: 프로필별 SPEC 선택을 고치자 `~/app` 의 APP-SPEC 이탈이 처음 보였다).

## 5. 끝맺음
- 표로 보고: 갱신한 것 / 새로 설치·등록한 것 / 보존한 것 / 남은 격차(이유 + 다음 행동).
- 커밋은 **단위로 나눈다** — `chore(hooks):` (복사본 갱신)과 `chore(setup):` (선언·규칙·ADR 반영)은 되돌리는 단위가 다르다.
- 남은 격차가 setup 영역이면 `/develop-setup` 을 안내한다. 이 스킬이 스택·도구를 정하지 않는다.

## 하지 않는 것
- 선언 없는 프로젝트에 훅만 복사하기 — 최신인데 아무것도 안 막는 상태가 된다
- `cgamja.json` 기존 값·`rules` 내용·프로젝트가 추가한 settings 항목 덮어쓰기
- 스택·도구 변경 제안, 스캐폴드, 기능 코드 수정
- 프로브 ✗ 를 갱신 실패로 보고 되돌리기 — 대개 새 검사가 오래된 격차를 처음 비춘 것이다

## 파일
| 파일 | 용도 |
|---|---|
| `scripts/drift.sh` | 네 축 대조(종료코드 0=격차 없음, 1=격차 있음). `--apply` 로 §2 규칙대로 적용 |
| develop-setup `scripts/hook-cases.sh` | 갱신 후 훅이 진짜 막는가 |
| develop-setup `scripts/smoke.sh` | 갱신 후 세팅 전체 |
