# review-seo — SEO·AI 검색 감사와 수정

claude-seo 에이전트들은 각자 한 렌즈만 본다. 이 스킬의 일은 (1) 감사 대상을 에이전트가 볼 수 있는 URL로 만들고, (2) 지금 상황에 필요한 렌즈만 고르고, (3) 서로 어긋나는 보고를 합쳐 우선순위를 매기고, (4) 코드로 고칠 수 있는 것을 고쳐 다시 재는 것이다. 에이전트 보고를 그대로 붙여 넣는 것은 리뷰가 아니다.

## 1. 대상 만들기

프로덕션 URL이 지금 코드와 같다면 그 URL을 쓴다. 아니면(배포 전, 브랜치 작업 중) **빌드 결과를 로컬로 띄운다** — 에이전트는 curl로 읽으므로 localhost면 충분하다.

```bash
pnpm build            # 또는 npm run build — 프로젝트 README/CLAUDE.md의 빌드 명령
python3 -m http.server 3100 --directory out   # Next 정적 export=out, Vite/Astro=dist
```

개발 서버(`next dev`)로 감사하지 마라 — 폰트 프리로드·CSS 청크·메타 병합이 프로덕션과 다르다. 감사 후 `pkill -f "http.server 3100"`.

에이전트에 넘길 사실을 먼저 모은다: 프레임워크와 출력 폴더, 소스에서 메타·스키마·sitemap·robots가 있는 파일 경로, 그리고 **의도된 것들**(빈 alt인 장식 이미지, 아직 null인 링크, 인라인 초기화 스크립트, 단일 언어라 hreflang 없음, 문안 규칙). 의도된 것을 안 알려주면 보고의 절반이 "결함 아님"을 걸러내는 데 쓰인다.

## 2. 렌즈 고르기 — 고정 목록이 아니다

`references/agent-picker.md`를 읽고 상황에 맞는 에이전트만 고른다. 요지:

| 상황 | 렌즈 |
|---|---|
| 어떤 페이지든 첫 감사 | `seo-technical`(크롤·메타·canonical·404·sitemap·robots) + `seo-schema`(JSON-LD) |
| 브랜드가 일반 명사거나 AI 답변 인용이 목표 | `seo-geo` (정의문·인용 가능 문단·엔티티·llms.txt) |
| 애니메이션·폰트·이미지·번들을 바꾼 뒤 | `seo-performance` (LCP 후보·프리로드·렌더 차단·DOM 크기) |
| 글이 많은 페이지(블로그·가이드) | `seo-content` (E-E-A-T·가독성·얇은 콘텐츠) |
| 첫 화면 구성이 바뀜, 모바일 의심 | `seo-visual` (스크린샷·above-the-fold) |
| 매장·지역 서비스 / 상품 판매 / 다국어 | `seo-local`·`seo-maps` / `seo-ecommerce` / `seo-hreflang` |
| 기준선(baseline)이 있는 재감사 | `seo-drift` |
| 키워드·주제 전략 | `seo-cluster`·`seo-plan` 스킬 (에이전트가 아니라 스킬) |

두 개면 충분한 상황에 여섯 개를 돌리지 마라 — 에이전트당 5분·5~10만 토큰이고, 겹치는 보고는 합치는 비용만 늘린다. 반대로 사용자가 "SEO가 최우선"이라 했으면 technical·schema·geo·performance 네 개가 기본이다.

고른 에이전트는 **한 메시지에서 전부 스폰**한다(직렬로 돌리면 시간이 배로 든다). 프롬프트에는 localhost URL, 검사할 경로 목록, 소스 경로, 의도된 것 목록, "파일을 고치지 말고 파일 참조와 함께 우선순위 목록으로 보고"를 넣는다. 사용자가 원하는 렌즈가 하나뿐이면(예: "스키마만") 그것만.

기다리는 동안 `scripts/inspect_html.py`로 기준선 숫자를 찍어 둔다 — 고친 뒤 같은 숫자와 비교한다.

```bash
python3 ~/.claude/skills/review-seo/scripts/inspect_html.py out / /blog/
```

## 3. 보고 합치기

에이전트들은 서로를 모른다. 합칠 때 볼 것:

- **충돌은 최신 정책 쪽으로.** 예: geo가 FAQPage 스키마를 권하고 schema가 "FAQ 리치 결과는 종료"라 하면 schema를 따른다. 같은 파일을 두 에이전트가 다르게 고치라 하면 둘 다 만족하는 형태를 찾고, 없으면 사용자에게.
- **세 통으로 나눈다.** ① 코드로 지금 고칠 수 있는 것 ② 사실·문안 소유자의 판정이 필요한 것(회사 표기, 가격, 제목 문구, 정책 공개) ③ 사이트 밖의 일(스토어 등록, 유튜브, 서치콘솔 제출). ②③은 고치지 말고 목록으로 넘긴다.
- **사실을 지어내지 않는다.** 스키마의 `sameAs`·평점·전화번호·가격처럼 소스에 없는 값은 에이전트가 권해도 넣지 않는다. 프로젝트에 "null이면 그리지 않는다" 같은 규칙이 있으면 그것이 우선.
- **문안 규칙이 있으면 그 테스트가 심판.** 에이전트가 제안한 문장을 넣기 전에 문안 테스트를 돌린다.

## 4. 고치기와 재검증

자주 나오는 것과 고치는 방향(자세한 건 `references/common-fixes.md`):

- 스크롤 애니메이션이 초기 HTML에 `opacity:0`을 남김 → 마운트 전에는 보이는 상태로 렌더하고, JS가 켜졌을 때만 CSS 게이트(`html[data-motion]`)로 숨긴다. `once:true`로 바꾸는 것은 사용자 결정.
- 글자별 span + sr-only 사본 → 문장이 두 번 들어간다. 사본을 없앤다.
- next/font 한글 조각 프리로드 폭주 → `preload: false`.
- 하위 페이지가 루트 OG를 물려받음 → Next는 openGraph를 깊은 병합하지 않는다. 페이지마다 채우는 헬퍼.
- 404·빈 자리 페이지가 홈 canonical·index를 물려받음 → 독립 메타데이터.
- 정적 export에서 route.ts의 응답 헤더는 버려짐 → 호스팅(netlify.toml 등)에서 MIME 지정.

고친 뒤: 빌드 → `inspect_html.py`로 기준선과 비교(본문 opacity:0·반복 문장·NO-ALT·H1 수·폰트 프리로드) → 브라우저에서 콘솔 오류·하이드레이션 경고 0건 확인 → 프로젝트 검증 명령(`pnpm verify` 등) 통과. 큰 감사 뒤 재감사는 `seo-drift`나 기술 에이전트 하나로 족하다.

## 5. 보고

```
## SEO 감사 결과 — <대상> (<렌즈 목록>)
**가장 큰 문제 하나** (한 문단, 근거 숫자)
**고친 것** (항목마다 파일)
**팀 판정이 필요한 것** (사실·문안·정책)
**사이트 밖** (스토어·서치콘솔·콘텐츠)
**기준선 → 결과** (inspect_html 숫자 비교)
```

결정 사항은 프로젝트의 ADR이나 결정 기록에 남긴다 — 특히 디자인·움직임과 SEO가 부딪혀 SEO를 택한 경우, 다음 사람이 애니메이션을 되돌리지 않도록.

## 주의

- 에이전트가 "파일을 고쳤다"고 하면 확인해라. 이 스킬의 에이전트 프롬프트는 읽기 전용이어야 한다.
- 점수(74/100 같은)는 에이전트마다 기준이 달라 비교 불가. 사용자에게는 숫자보다 "무엇이 얼마나"를 말한다.
- 프로덕션 도메인이 옛 사이트를 가리키고 있을 수 있다. 감사 대상이 지금 코드인지 먼저 확인한다.
