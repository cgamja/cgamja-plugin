# review-cgamja — 철학 준수 게이트

코드가 이 사용자의 문서화된 철학에 부합하는지 검사하고, 부합할 때까지 수정 루프를 돌린다. 철학의 축이 "강제되지 않는 원칙은 철학이 아니다"이므로, 이 스킬이 린트가 못 잡는 규칙들의 강제 수단이다.

## 절차

### 1. 대상 결정

- git 레포면: `git diff HEAD` (스테이징 포함 변경분). 변경분이 없으면 직전 커밋(`git show`). 사용자가 파일/디렉토리를 지목했으면 그것
- git이 아니면: 사용자가 지목한 파일들
- 대상이 비어 있으면 여기서 멈추고 사용자에게 무엇을 검사할지 물어라

### 2. 검사 (서브에이전트)

`reviewer-cgamja` 에이전트를 Agent 도구로 스폰한다. 프롬프트에 반드시 포함할 것:
- 검사 대상 (diff 요약 또는 파일 목록 — 에이전트가 직접 읽을 수 있게 경로로)
- 철학 문서 루트 경로: **이 플러그인의 `docs/spec/`** (절대 경로로 넘긴다 — 이 SKILL.md가 있는 플러그인 루트 아래 `docs/spec/`. 프로젝트에 별도 사본이 있으면 그것을 우선)
- 웹 프로젝트인지 앱(RN) 프로젝트인지 (WEB-SPEC vs APP-SPEC 선택용)

검사 자체를 메인 컨텍스트에서 직접 하지 마라 — 새 컨텍스트의 에이전트가 문서만 근거로 판정해야 "작성자가 자기 코드를 봐주는" 편향이 없다.

### 3. 판정 처리

- **PASS**: 판정 요약을 사용자에게 전달하고 원래 하던 작업(커밋 등)을 진행한다
- **FAIL**: 위반 목록을 사용자에게 보여주고 수정한다
  - blocker/should는 에이전트의 "제안"대로 수정하되, 제안이 틀렸다고 판단되면 수정하지 말고 이유와 함께 사용자에게 보고
  - 수정 후 **재검사(2단계)를 1회 더** 돌린다. 두 번째도 FAIL이면 루프를 멈추고 남은 위반과 이유를 사용자에게 넘긴다 — 무한 수정 루프 금지
- **"문서에 규칙이 없는 영역"** 이 보고되면: 고치지 말고 사용자에게 전달한다. 철학 문서에 추가할지는 사용자의 결정이다 (PHILOSOPHY.md의 성장 규칙)

### 4. 최종 보고

에이전트 보고를 그대로 붙이지 말고 요약해라: 판정, 위반 몇 건 중 몇 건 수정, 남은 것, 철학 문서 제안 사항. 위반→수정 과정에서 반복된 패턴이 있으면 "GOOD-BAD-PATTERN.md에 사례로 추가할까?"를 제안한다 — 실전 사례로 토스 예제를 교체하는 게 이 철학의 성장 방식이다.

## 주의

- 이 스킬은 철학 대조 전용이다. 버그·보안·성능 리뷰 요청은 일반 코드 리뷰로 처리해라
- 판정을 통과시키기 위해 철학 문서 쪽을 수정하는 것은 금지 — 문서 개정은 별도 대화로
