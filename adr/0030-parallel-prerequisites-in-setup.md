# ADR 0030 — 병렬 작업의 전제를 develop-setup이 깐다

- 상태: 제안 (2026-08-31)
- 관련: adr/0027 §3(worktree 병렬), adr/0014(선언 기반 세팅), adr/0029(게이트 전진), reports/retro-2026-08-31_evening.md

## 문제

`workflow.md` 2-P는 독립 change의 병렬 작업을 규정한다:

> 독립 change마다 터미널을 띄워 `claude --worktree <change-slug>` 세션에서 각각 `/develop-fe`
> 세팅: `.claude/worktrees/`를 gitignore, `.worktreeinclude`에 `.env`(worktree별 PORT)

세팅 한 줄이 본문에 묻혀 있고, **그것을 실제로 까는 주체가 없다.** `develop-setup`이 만드는 10개 항목(SKILL.md §2)에 병렬 전제가 없다.

2026-08-31 `~/skill-test` 실측 — 하루 종일 개발하고 61커밋을 쌓은 레포의 상태:

| 2-P가 요구하는 것 | 실제 |
|---|---|
| worktree | **메인 하나뿐** (`git worktree list` 1행) |
| `.worktreeinclude` | **없음** |
| `.claude/worktrees/` + gitignore 항목 | **없음** |
| worktree별 dev 포트 | **없음** — `vite.config.ts`에 `server` 블록 자체가 없어 전부 5173 |

즉 2-P는 **문서상으로만 존재**했다. 사용자가 병렬을 시도하려 해도 판정 3(환경 싱글턴 충돌 — dev server 포트)에 무조건 걸린다. 포트가 하나뿐이므로 두 번째 세션은 dev 서버를 띄우는 순간 충돌하거나, vite가 조용히 5174로 옮겨 뜬 뒤 **증거 캡처 스크립트가 5173을 때린다**(선언 `evidence.screenshot`이 URL을 인자로 받으므로 세션이 자기 포트를 알아야 한다).

같은 런에서 사용자의 목표가 "병렬 개발이 되게 하는 것"으로 확인됐다. 전제가 없으면 목표에 도달할 수 없다.

## 결정

병렬 전제를 **선언 + 세팅 항목**으로 승격한다. 2-P는 그 선언을 읽기만 한다(adr/0014 세 층 구조).

### 1. 선언 (`.claude/cgamja.json`)

```json
"parallel": {
  "worktrees": ".claude/worktrees",
  "port_env": "PORT",
  "max_concurrent": 3
}
```

병렬을 쓰지 않는 프로젝트는 `"parallel": null` — 2-P는 그때 "병렬 세팅 없음, 직렬로 진행"이라고 보고하고 직렬로 간다. 없는 강제 수단은 `null`이라는 0014 규칙 그대로다.

### 2. `develop-setup`이 만드는 것 (SKILL.md §2에 11번 추가)

| 만드는 것 | 내용 |
|---|---|
| `.gitignore` 추가 | `.claude/worktrees/`, `.env` |
| `.worktreeinclude` | worktree마다 복사할 **비추적** 파일 목록 — 최소 `.env` |
| `.env` (worktree별) | `PORT=<빈 포트>` 한 줄. 추적하지 않는다 |
| dev 서버 포트 파라미터화 | 러너 설정이 `port_env`를 읽게 한다. 없으면 기본 포트로 폴백 |

**`strictPort`를 켠다.** 포트가 이미 잡혀 있으면 조용히 옮겨 뜨는 대신 실패해야 한다 — 조용한 이동이 위 §문제의 "캡처가 엉뚱한 포트를 때린다"를 만든다. 실패는 보이고, 조용한 이동은 안 보인다.

### 3. 프로브 (`scripts/smoke.sh`에 1종 추가)

만들었다가 아니라 작동한다를 보이는 것이 develop-setup의 규칙이다(SKILL.md §3). 병렬 프로브:

> worktree 2개를 만들고 각각 다른 `PORT`로 dev를 띄워 **둘 다 응답하는가.** 하나라도 못 뜨거나 같은 포트로 뜨면 ✗.

끝나면 worktree를 정리한다.

### 4. `workflow.md` 2-P 진입 체크

병렬 가능 판정 4개 앞에 0번을 둔다:

> 0. `parallel` 선언이 `null`이거나 `.worktreeinclude`가 없으면 → **직렬**. 병렬을 원하면 `/develop-setup`으로 전제부터 깐다.

## 버린 대안

- **포트 자동 탐색에 맡기기** — vite는 이미 그렇게 동작한다(5173 점유 시 5174). 그런데 세션이 자기 포트를 모르면 증거 캡처·브라우저 검증이 엉뚱한 곳을 본다. 자동 탐색은 사람에겐 편의지만 에이전트에겐 **관측 불가능한 상태**다.
- **worktree를 메인 세션이 직접 만들기** — adr/0027 §3이 이미 금지했다(격리는 하네스의 일). 이 ADR은 하네스가 만든 worktree가 **작동하게** 하는 전제만 깐다.
- **2-P 본문에 세팅 절차를 더 자세히 적기** — 오늘 실패한 방식이다. 문서에 적힌 세팅은 아무도 실행하지 않는다. 실행 주체(develop-setup)와 검증 수단(smoke 프로브)이 있어야 한다.
- **브랜치만으로 병렬(worktree 없이)** — 한 워킹트리에서 브랜치를 갈아타는 것은 병렬이 아니라 직렬이다. 두 세션이 같은 디렉터리를 공유하면 checkout이 서로의 작업을 지운다.

## 비용

- 세팅 항목이 10개에서 11개로 는다. 병렬을 안 쓰는 프로젝트에는 불필요 — `parallel: null`로 끄고, 그때 이 항목은 건너뛴다.
- `strictPort`를 켜면 사람이 수동으로 `npm run dev`를 두 번 띄울 때 두 번째가 실패한다. 이전에는 조용히 다른 포트로 떴다. **의도된 변경**이지만 사람에겐 마찰로 느껴질 수 있다 — `.env`의 `PORT`를 바꾸면 된다는 안내를 `CLAUDE.md` 명령 단락에 한 줄 넣는다.
- worktree마다 `node_modules`가 필요하다. 디스크와 설치 시간이 change 수만큼 는다. `max_concurrent: 3`이 상한 역할을 겸한다.

## 이 ADR만으로는 병렬이 빨라지지 않는다

2026-08-31 런에서 하루를 직렬로 묶은 것은 worktree 부재가 **아니라** 사람 대기 181분(36%)이었다(adr/0029 §문제). 격리를 깔아도 두 세션이 각각 사람의 차단형 질문을 기다리면 총 대기는 줄지 않고 컨텍스트 스위칭만 는다.

**0029(전진)와 0030(격리)은 한 쌍으로만 값이 나온다.** 0029가 대기를 없애 병렬로 쓸 시간을 만들고, 0030이 그 시간을 쓸 자리를 만든다. 어느 하나만 반영하면 재검토 조건이 발동할 것으로 예상한다.

## 재검토 조건

- 병렬 실행에서 포트·`.env` 충돌 **2회** → `.worktreeinclude` 방식(파일 복사)을 버리고 포트를 worktree 경로 해시로 도출한다.
- worktree 간 머지 충돌 **2회** → 2-P 판정 2(semantic 표면)의 기준을 좁힌다 — 오늘 레포처럼 모든 화면이 `App.tsx`·토큰·공용 테스트를 공유하면 애초에 병렬 대상이 아니다.
- `parallel` 선언을 깔았는데 실제 병렬 세션이 **3주간 0회** → 전제가 아니라 진입 경로(`claude --worktree`)가 문제다. 재조사.
- 병렬 2세션을 돌렸는데 총 소요가 직렬 대비 줄지 않은 런 **2회** → 0029가 반영됐는지부터 확인하고, 됐다면 병렬 자체를 재평가한다.
