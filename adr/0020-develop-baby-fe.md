# 0020. develop-baby-fe — MVP 경량 경로: 절차를 끄는 별도 스킬, 비용·속도 우선

- 상태: 제안
- 날짜: 2026-08-26
- 관련: 0012·0016(렌즈 비용), 0011(모델 라우팅 — 의도적 하향), 0014(선언 키), 0008(계약 — 최소 규칙으로 유지)
- 검증: 없음(신규). 다음 검증: MVP 프로젝트 1회 런에서 총비용·재작업 횟수 실측(`reports/`)

## 맥락
사용자 실사용 기록(2026-08-25 메모): "간단한 MVP 제작에도 너무 큰 힘을 쓰는 느낌. develop-fe랑 아예 분리되어, 이 스킬을 쓰면 가벼운 MVP. 성능보단 비용과 속도에 기반. 최소한의 리뷰·디자인 검증만." 비용 좌표 리서치(2026-08-25, `reports/`)가 이를 뒷받침한다:
- cgamja Tier-1은 $0.74, Tier-2는 $30~45 — **그 사이가 비어 있다.** "화면 하나 대충 돌아가게"는 Tier-1(diff 한 문장)보다 크고 Tier-2 풀 절차(스펙·red 게이트·렌즈 6개·증거 매트릭스)보다 훨씬 작다.
- 리뷰 렌즈는 2~4개가 한계효용 정점(CodeX-Verify: +14.9 → +11.2pp 체감), 같은 관점의 반복 샘플링(self-consistency)은 +0.4~1.6%뿐으로 비추천 — 최소 리뷰 1렌즈 1회는 근거 있는 절단선이다.
- BMAD식 "항상 전 파이프라인"은 반례($85~200) — **티어·모드로 절차를 켜고 끄는 설계가 정답 방향**이라는 결론과 일치.
4세션 회고(2026-08-25~26, ~/app 실사용)에서 Tier-2 한 change에 약 3시간·커밋 24~33개·테스트 승인 피로("테스트 수정하고 그런거 다 Yes로 해")가 실측됐다. 이 무게는 프로덕션 레포에서는 값을 했지만(렌즈가 실버그 3건 적발) MVP에는 과잉이다.

## 결정
1. **별도 스킬 `develop-baby-fe`로 분리한다.** develop-fe의 티어 하향이 아니다 — 진입점 자체를 나눈다(사용자 요구: "아예 분리"). develop-fe는 프로덕션 레포·티켓 기반 작업, baby는 MVP·프로토타입·데모·실험. 오발동은 두 스킬 description의 상호 배타 트리거로 막는다.
2. **절차는 여섯 단계, 사람 게이트는 질문 최대 1회뿐**: 탐색(기존 코드 grep, 질문 0~1회) → 구현 → L1 정확성 렌즈 1회(blocker만 수정, 재실행 없음) → `commands.verify` 1회(**리뷰 반영까지 끝난 최종 코드에서** — 미검증 diff 커밋 방지; 선언 null이면 생략하고 그 사실을 보고) → 스크린샷 1장(가능한 수단이 있을 때) → 커밋 1~3개(단계 단위). PR은 사용자가 요청할 때만.
3. **끄는 것**: 티어 판정, OpenSpec change, red 게이트(테스트 먼저), 렌즈 다중·재실행, Figma 스냅샷 절차(있으면 참고만), 증거 매트릭스(뷰포트×모드), ce-* 오케스트레이션(brainstorm·code-review 등).
4. **유지하는 최소 규칙 4개** — MVP가 나중에 프로덕션으로 승격될 때의 비용을 막는 하한선: ① 계약 생성물이 선언돼 있으면(`contract.generated`) 생성물만 import ② 기존 테스트는 초록 유지(깨뜨리면 멈춤) ③ 새 의존성은 질문 ④ 만들기 전에 기존 컴포넌트·유틸 grep.
5. **에스컬레이션은 안내이지 자동 전환이 아니다**: API 계약을 새로 만들거나 바꿔야 하는 순간, 또는 여러 화면·공유 상태가 엮이는 순간 **멈추고** `/develop-fe`를 안내한다. 이유: 그 두 조건이 4세션 회고에서 확인된 "무거운 절차가 실제로 값을 한" 지점이다(계약 결함·상태 배선 버그를 렌즈가 적발).
6. **선택 키 `mode: "baby-default"`**(`.claude/cgamja.json`): 선언돼 있으면 그 프로젝트의 코드 변경 요청 기본 진입을 baby로 안내한다. 세팅 스킬이 묻지 않는다 — 사용자가 손으로 넣는 선택 키다. **우선순위: 결정 1의 제외 조건(프로덕션 티켓·API 계약 신설·다중 화면)이 `baby-default`보다 항상 위다** — 선언이 있어도 그 요청은 develop-fe로 라우팅한다(두 스킬 description에 동일하게 명시).
7. **L1 렌즈 모델은 `sonnet`을 명시한다** — 0011의 기본(리뷰 렌즈 `opus`)에서 의도적 하향. 근거: 비용 우선 모드이고, PoLL 판사 패널 연구(작은 모델 패널이 단일 대형 심판보다 인간 판정 상관 높고 비용 1/7)가 방향을 지지. persona는 `agents/reviewer-correctness.md`를 그대로 재사용한다(즉석 리뷰어 제작 금지 규칙 유지).
8. **목표 비용 <$5/작업**을 스킬 본문에 명시한다 — 사용자가 baby/develop-fe를 고르는 판단 근거.

## 전제
- MVP 코드는 버려지거나, 살아남으면 develop-fe의 retrofit(계약 상태 C, adr/0008) 대상이 된다. 최소 규칙 ①이 그 비용을 절반으로 줄인다는 가정.
- 세팅(`/develop-setup`)이 없어도 동작한다 — 선언 키가 null이면 해당 단계를 생략하고 보고한다(멈추지 않는다). 프로덕션 하한선이 아니라 MVP이기 때문.

## 재검토 조건
- baby로 만든 코드가 develop-fe change에서 retrofit 2회 → 최소 규칙에 "계약 DRAFT 스텁 1장" 추가 검토
- baby 산출물의 버그로 같은 작업 재실행 2회 → L1 모델 상향 또는 L6 계약 렌즈 추가(2~4개 정점 안쪽)
- 프로덕션 레포 작업이 baby로 오발동 2회 → 두 스킬 description 트리거 재조정
- 실측 비용이 $5를 2회 초과 → 절차에서 더 뺄 것을 찾는다(스킬의 존재 이유가 비용이다)
