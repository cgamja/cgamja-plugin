# ADR 0036 — 검사는 git 훅을 못 까는 레포에서도 살아남아야 한다

- 상태: 제안 (2026-09-20)
- 관련: adr/0031(산문 규칙은 기계로 — 커밋 수 경고), adr/0014(프로젝트 선언), adr/0033(복사본 갱신 경로), care-app 2026-09 실측

## 문제

adr/0031은 "change당 커밋 4~8개"를 산문에서 pre-push 경고로 내렸다. 그런데 그 경고는 `templates/git-hooks/pre-push` **안에만** 있다.

care-app은 팀(PM)이 `.githooks/pre-commit`·`pre-push`를 소유하고 수정을 금지한다. 오버레이는 옳게도 workflow 0-b(훅 설치)를 껐다. 그 순간 pre-push에 들어 있던 세 검사 중 둘은 프로젝트가 따로 옮겨 놓았지만(메시지 형식 → commit-msg, 테스트 혼입 → CI 스크립트) **커밋 수 경고는 아무도 옮기지 않았다.** 결과: Tier-2 PR 12건 전원이 상한 초과(13~66, 중앙값 21). adr/0031이 고친 바로 그 문제가 같은 모양으로 재발했고, 이번에도 사람이 나중에 세어 보고 알았다.

근인은 검사가 **배달 수단(git 훅)에 묶여 있다**는 것이다. 훅을 못 까는 레포는 드물지 않다 — 팀 소유 훅, husky가 이미 있는 brownfield, 훅을 공유하지 않는 모노레포.

## 결정

1. "나가는 커밋 검사"(메시지 형식 · feat/fix의 테스트 혼입 · 커밋 수 경고)를 **`templates/scripts/check-commits.sh <base> <head>`** 로도 제공한다. 내용은 pre-push 2-a~2-c와 같다.
2. workflow 0-b: 훅을 설치할 수 없는 레포면 그 스크립트를 프로젝트 `scripts/`에 두고 **CI(PR 범위)와 Stop 훅에서** 부른다. 훅을 못 깐다는 이유로 검사가 사라지지 않게 한다.
3. pre-push 템플릿은 그대로 둔다(이미 깐 프로젝트를 깨지 않는다). 두 곳의 검사가 어긋나지 않게 하는 일은 `/develop-update`(adr/0033)의 몫이다.

## 버린 대안

- **pre-push가 스크립트를 호출하도록 일원화**: 옳은 종착점이지만 새 브랜치 첫 push의 범위(`--not --remotes`)를 base/head 두 인자로 옮기는 일이 끼고, 이미 설치된 복사본이 전부 갱신 대상이 된다. 이번엔 병행으로 두고 재검토 조건에 건다.
- **오버레이가 알아서 옮기게 두기**: care-app이 그렇게 했고, 셋 중 하나를 빠뜨렸다. 빠뜨릴 수 있는 구조가 결함이다.

## 비용

같은 검사가 두 파일에 있다 — 드리프트 위험. `/develop-update`의 대조 목록에 `templates/scripts/`를 넣는 일은 후속이다(이번 변경에 없음).

## 강제

- workflow 0-b의 분기 문장 **[사람 — 세션 시작 점검]**. `develop-setup` 대조표에 "훅 설치 불가 → 스크립트 + CI 호출 제안" 항목을 넣는 일은 **이번 변경에 없다**(후속 — 산문 강제라는 빚을 아래 재검토 조건이 센다).
- care-app: `scripts/check-commits.sh`에 커밋 수 경고 추가, `ci.yml`이 이미 호출 중 **[CI]**.

## 재검토 조건

- 두 파일의 검사가 어긋난 채 발견됨 1회 → pre-push가 스크립트를 호출하도록 일원화.
- 훅 설치 불가 레포가 3개째 → 0-b의 기본 경로를 "스크립트 + CI"로 뒤집고 훅은 선택으로.
