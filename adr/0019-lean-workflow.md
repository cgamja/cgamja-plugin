# 0019. 워크플로우 다이어트 — 시작 fast-path, 단계 단위 커밋, 리뷰 반영 배치, 계획 컨텍스트 예산

- 상태: 제안
- 날짜: 2026-08-26
- 관련: 0001(OpenSpec 척추), 0012·0016(리뷰 렌즈·예산), 0017·0018(훅·게이트 — 같은 회고에서 나온 형제 개정)
- 검증: 실사용 4세션 회고(2026-08-25~26). 수정 후 재검증: 다음 Tier-2 change 1개에서 첫 가시 보고 ≤30초, change당 커밋 ≤8, 미검증 리뷰 반영 diff 0, 계획 단계 컨텍스트 ≤15%

## 맥락
1. **시작이 지시를 이긴다.** 사용자가 "SIM-139. 바로 브랜치 파서 시작"이라고 명시했는데, 0장 점검(세팅 4종·git·openspec·solutions·typecheck·계약·디자인) + 레포 규약(티켓 사본 전체 읽기 + 트래커 실시간 조회)을 순서대로 수행하느라 92초간 브랜치 명령 0회·가시 출력 거의 0으로 인터럽트당했다. 같은 티켓을 로컬 사본 3회 + 트래커 MCP 2회로 **이중 조회**했다. "세션 시작 30초"는 표기일 뿐 구조적으로 불가능했다.
2. **커밋 과다.** "task 1개 = 커밋 1개" + 테스트 별도 커밋 + 세팅 수리·훅 우회·리뷰 반영 커밋이 겹쳐 change당 커밋 24~33개. 사용자 피드백: "커밋도 너무 많이 하지 않게. 리뷰는 여러 번 해도 수정은 한 번에."
3. **리뷰 반영 꼬리가 미검증으로 출하.** blocker 반영 커밋이 새 blocker를 만들고, 재실행 1회 상한 뒤의 마지막 반영 커밋들이 기계 리뷰 없이 PR에 들어갔다(스스로 명시하긴 했다).
4. **계획 단계에서 컨텍스트 20%+.** 스냅샷·스펙 전문·티켓 본문이 본 컨텍스트에 쌓인다. 사용자 메모: "CONTEXT WINDOW가 한 세션에서 너무 빨리 참."
5. **propose 경계 충돌.** OpenSpec propose 지시문("Do not edit project code")과 절차(propose 중 계약 파일 수정+생성)가 정면 충돌 — 모델이 매번 재량 판단.
6. **폰트 대조 공백.** 디자인 폰트가 시스템 폰트로 대체된 것을 렌즈 6개·SSIM 검증이 전부 놓치고 사람 눈이 잡았다 — §6 SSIM 항목이 "98~99.5%는 대개 폰트 렌더링 차이"라며 오히려 합리화 여지를 주고 있었다.

## 결정
1. **시작 fast-path.** 사용자 지시에 즉시 실행 가능한 첫 행동(브랜치 생성, 특정 파일 열기 등)이 있으면 **그것이 첫 도구 호출**이다. 0장 점검은 그 뒤에(가능하면 병렬로) 하고, **첫 가시 보고(티어+비용 한 줄)는 30초 안에** 낸다. 외부 트래커가 있는 레포에서는 시작 시점 조회를 **한 경로로**: 스코프는 레포 사본, 실시간 상태는 트래커 — 같은 내용을 두 번 읽지 않는다(역할 분담은 레포 규약이 정하고, 절차는 중복 조회만 금지).
2. **단계 1개 = 커밋 1개.** change당 기본 4~8개: `docs(spec)` 1 / `test(scope)` 1~3(red는 시나리오를 묶어 배치로) / `feat(scope)` 1~3(연속 task를 묶어서) / `fix(review)` 1 / 필요시 `chore` 1. task마다 커밋하지 않는다. 시행착오·세팅 수리·중간 재작업은 독립 커밋으로 남기지 않고 다음 단계 커밋에 합친다. **테스트/구현 커밋 분리는 유지**(0018의 변조 방지 담당). change당 커밋 10개 초과는 재검토 신호.
3. **리뷰 반영은 배치 1회 + 잔여 diff 0.** 렌즈 전체의 blocker를 모아 수정 패스 1번 → `fix(review)` 커밋 1개 → 해당 렌즈 재실행 1회. 재실행 이후에 새 수정 커밋이 생기면 **그 diff가 기계 리뷰를 통과하지 않았음을 판정 줄에 명시하고, 잔여 diff가 0이 될 때까지 커밋을 재실행 이전으로 몰아넣는 것을 기본**으로 한다(예외는 0012의 assertion 보강 경로).
4. **계획 컨텍스트 예산.** 탐색·티켓 본문·스냅샷 요약은 서브에이전트가 읽고 **요약만** 본 컨텍스트로 받는다(기존 3-4 규칙을 계획 단계에 명시 적용). 스펙 delta·summary.md 같은 작업 원천만 본체가 직접 읽는다. 계획(1~3단계) 종료 시점 컨텍스트 사용량을 첫 보고에 한 줄로 적는다 — 15%를 넘으면 무엇을 서브에이전트로 내렸어야 했는지 기록.
5. **propose는 planning boundary를 지킨다.** propose 단계에서는 프로젝트 코드·계약 파일을 편집하지 않는다. DRAFT 스텁 작성·`contract.generate` 실행은 **apply의 첫 task**로 옮긴다(스펙에는 스텁 요약만).
6. **Figma 대조에 폰트 패밀리.** computed style 대조 항목에 font-family를 포함하고, 디자인 폰트가 프로젝트에 없으면 **대체 사실을 첫 UI task 보고에 명시**한다(summary.md의 보고 의무를 절차가 강제). SSIM 구간 해석("폰트 렌더링 차이")은 폰트 패밀리 일치가 확인된 뒤에만 적용한다.

## 재검토 조건
- fast-path로 시작한 작업이 세팅 누락 때문에 되돌아간 사례 2회 → 0장 필수 항목을 fast-path 앞으로 복귀.
- 배치 red(시나리오 묶음)에서 실패 원문이 섞여 사람이 판독 못 한 사례 2회 → red 배치 크기 상한(시나리오 3개).
- feat 커밋 묶음이 bisect·리뷰를 어렵게 한 사례 2회 → task 단위 커밋으로 부분 복귀.
- 잔여 diff 0 규칙 때문에 재실행이 2회를 넘는 change 2개 → 상한 유지하되 잔여 diff 명시로 완화.
