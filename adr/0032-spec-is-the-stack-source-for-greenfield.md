# ADR 0032 — 빈 레포에서 스택의 원천은 SPEC이다

- 상태: 제안 (2026-08-31)
- 관련: adr/0014(스택은 정하지 않고 읽는다), adr/0029(게이트 전진), adr/0031(산문 규칙 금지), reports/retro-2026-08-31_evening.md

## 문제

2026-08-31 `~/skill-test` 는 **빈 레포**에서 시작했다. `develop-setup`이 세팅하고 `develop-fe`가 하루 종일 개발해 61커밋을 쌓았다. 그 결과물을 `docs/spec/WEB-SPEC.md`와 대조하면:

| SPEC | 프로젝트 | `docs/adr/` 기록 |
|---|---|---|
| TypeScript 5.x **(strict)** | `strict` 키가 어느 tsconfig에도 없음 | 없음 |
| 프레임워크 기본값 **Next.js** | React + Vite SPA | 없음 |
| **TailwindCSS 4.x** | 순수 CSS + 토큰 | 없음 |
| cn (clsx + tailwind-merge) | 없음 | 없음 |
| Tanstack Query 5.x · Zustand 5.x | 없음 | 없음 |
| Prettier | 없음(린터 `--fix`로 대체) | 없음 |

WEB-SPEC 머리말이 정한 것:

> 프로젝트가 이 스펙에서 벗어날 때는 해당 프로젝트의 `adr/`에 기록한다

프로젝트 `docs/adr/`에는 0001(도메인 구조)·0002(계약)·0003(증거) 셋뿐 — **스택 이탈 ADR 0건.** 이탈 자체보다 **이탈이 판단으로 남지 않은 것**이 문제다. 특히 프레임워크는 SPEC 표가 "대외 서비스 — SEO·초기 로딩·**OG 태그**가 중요 → Next.js"와 "서버 없이 정적 호스팅 → Vite SPA" 두 행 모두에 걸리는 경우였고, SPEC은 "판단이 안 서면 Next.js"라고 못 박았다. 어느 쪽을 골랐든 기록이 필요했다. (같은 런에서 "OG 태그 없음"이 출시 블로커로 따로 발견됐다 — 같은 뿌리다.)

### 근인 둘

**(a) `develop-setup` §0 "발견"은 *기존 레포*를 읽는 절차다.** 매니페스트·프레임워크·러너·린터를 읽어 발견 표를 만든다. 빈 레포에는 발견할 것이 없어 표가 비고, §1 대조표는 "철학 원칙 ↔ 강제 수단"만 본다 — **스택 ↔ SPEC 축이 아예 없다.**

**(b) 스캐폴더가 스택을 정해버린다.** §0은 "빈 폴더면 '스캐폴드가 필요합니다 — 어떤 것으로?'를 묻고 사용자가 고른 명령을 그대로 실행"이라고 한다. 실제로는 `npm create vite@latest . -- --overwrite ignore`가 실행됐고(그 과정에서 `PRD.md`를 지웠다가 복구), 그 스캐폴더의 기본값이 곧 스택이 됐다. SPEC을 참조하라는 지시가 그 시점에 없다. 게다가 스캐폴더 결과를 그대로 두어 `strict` 미설정이 살아남았다.

adr/0014의 "스택을 정하지 않는다"는 **brownfield에서 남의 스택을 존중하라**는 뜻이었는데, greenfield에서는 "아무도 정하지 않는다"로 잘못 작동했다.

## 결정

### 1. 빈 레포에서 스택의 원천은 `docs/spec/WEB-SPEC.md`(웹)·`APP-SPEC.md`(앱)다

스캐폴더를 묻기 전에 SPEC의 스택을 읽고 **그것을 기본 제안으로** 낸다. "어떤 것으로?"라는 백지 질문을 하지 않는다 — adr/0029 기준으로 답이 "알아서 해"로 돌아올 질문이다. 대신:

```
가정: SPEC 기본값대로 Next.js 16 + Tailwind 4 + TS strict 로 간다
근거: docs/spec/WEB-SPEC.md §Framework 표 첫 행(대외 서비스·SEO·OG) — 이 프로젝트는 랜딩이다
되돌리는 비용: 스캐폴드 직후면 낮다(코드 0줄). 개발 시작 후면 높다
```

반박이 오면 그때 바꾸고, 바뀐 값을 §3의 ADR로 남긴다.

### 2. 대조표(§1)에 **스택 축**을 추가한다

기존 대조표는 "철학 원칙 ↔ 강제 수단"이다. 여기에 SPEC이 정한 항목(언어·프레임워크·CSS·상태·번들러·러너·포맷터)마다 한 행:

| SPEC 값 | 이 프로젝트 값 | 판정 |
|---|---|---|
| TailwindCSS 4.x | 순수 CSS | **이탈 — ADR 필요** |

### 3. 이탈은 `docs/adr/`에 기록해야 세팅이 끝난다

"완료"의 정의에 넣는다. `smoke.sh` 프로브 11이 검사한다 — SPEC의 스택 항목이 매니페스트에 없고 `docs/adr/`에도 언급이 없으면 ✗. `strict`는 따로 본다(의존성이 아니라 설정이라 매니페스트에 안 나타난다).

### 4. 스캐폴드 결과를 그대로 두지 않는다

스캐폴더가 SPEC과 다른 값을 만들면(예: `strict` 미설정) 세팅이 그것을 고친다. 스캐폴더는 파일을 놓는 도구지 결정권자가 아니다.

## 버린 대안

- **SPEC 스택을 강제(예: Next 스캐폴더만 허용)** — SPEC 표 자체가 상황에 따라 Vite SPA를 허용한다. 목적은 판단을 없애는 게 아니라 **판단을 기록하게** 하는 것이다.
- **SPEC을 프로젝트로 복사해 심기** — SPEC은 사용자 소유의 단일 원천이고 복사본은 드리프트한다(같은 사실을 두 곳에 두지 않는다).
- **리뷰 2축이 잡게 하기** — 리뷰는 diff를 보지 *부재*를 못 본다. "쓰지 않은 Tailwind"는 diff에 없다(adr/0031과 같은 이유).
- **CLAUDE.md "가정" 절에 적는 것으로 충분하다고 보기** — 실제로 그 절에는 라우터·서버 상태·Playwright만 적혔고 Tailwind·Next·strict는 아예 언급되지 않았다. "가정"은 세팅이 *의식한* 것만 담는다 — 의식하지 못한 이탈은 대조표만 잡을 수 있다.

## 비용

- 빈 레포 세팅에 SPEC 읽기 1회 + 대조표 행 6~8개가 는다.
- SPEC 스택을 기본 제안으로 내므로, 사용자가 매번 다른 스택을 원한다면 반박 비용이 반복된다. 그때는 SPEC 자체가 틀린 것이므로 **SPEC을 고친다**(adr/0031: 지키지 않을 규칙은 없는 게 낫다).
- 프로브 11은 문자열 대조라 정밀하지 않다 — SPEC의 굵은 항목명을 매니페스트·ADR에서 찾는 수준이다. 오탐이 나면 ADR 한 줄로 해소되므로 비용이 낮은 방향의 오차다.

## 강제

`skills/develop-setup/scripts/smoke.sh` 프로브 11(`스택 ↔ SPEC 대조`) + `strict` 검사. 세팅 완료 조건에 포함된다.

## 재검토 조건

- 이탈 ADR이 이유 없이 형식적으로만 쌓이면(제목만 있고 "버린 대안·비용"이 없음) 프로브를 내용 검사로 올린다.
- 프로브 11의 오탐이 **2회** 나오면 문자열 대조를 버리고 선언(`.claude/cgamja.json`)에 `stack` 슬롯을 두어 명시 대조로 바꾼다.
- SPEC 기본값을 3개 프로젝트 연속으로 반박하면 SPEC의 그 항목을 재검토한다.
