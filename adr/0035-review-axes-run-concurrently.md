# ADR 0035 — 리뷰 축은 동시에 띄운다

- 상태: 제안 (2026-09-20)
- 관련: adr/0019(수정 패스 1번), adr/0026 §3(리뷰 2축), adr/0027(메인은 위임·판정만), care-app 2026-09 실측

## 문제

리뷰 2축(`review-cgamja` 철학 대조 · `code-review` 결함)은 입력이 같은 diff이고 서로의 결과를 읽지 않는다. 오버레이가 `review.extra_lenses`로 3축째(care-app: 팀 규약 6항목 자체 검증)를 얹어도 마찬가지다. 그런데 workflow 2장 5번은 ①②를 번호로 나열해 **순서처럼 읽힌다**, 그리고 실제로 순서대로 돌았다.

care-app 실측: 리뷰 서브에이전트 31회, 회당 중앙값 5.6~6.0분. 3축 직렬 + 재검사 직렬이면 change당 20~40분이 리뷰 대기다. 위임 28시간 다음으로 큰 덩어리이고, 고치는 데 드는 비용은 문장 하나다.

## 결정

1. 리뷰 축(기본 2축 + `review.extra_lenses`)은 **한 메시지에서 동시에** 띄운다.
2. 지적은 전부 모아 수정 패스 1번(adr/0019 그대로).
3. 재검사는 **지적이 나온 축만**, 역시 동시에. 지적이 없던 축을 확인차 다시 돌리지 않는다.

축의 내용·입력·판정 형식은 건드리지 않는다. 특히 오버레이가 팀 규약으로 가져온 축은 그 규약이 정한 그대로 돈다 — 이 ADR은 실행 순서만 바꾼다.

## 버린 대안

- **축 병합**(한 리뷰어가 철학+결함+팀 규약): 호출은 1회로 줄지만 렌즈 독립성을 잃는다. 2축으로 나눈 이유(adr/0026)가 그대로 반대 논거다. 팀 규약 축은 규약 소유자가 "별도 서브에이전트"를 요구할 수 있다.
- **수정 뒤 전 축 재검사**: 안전해 보이지만 재검사 1회 상한(adr/0019) 안에서 시간을 두 배로 쓴다. 수정 diff가 다른 축의 영역을 건드렸다면 판정 줄에 명시하는 기존 규칙으로 충분하다.

## 비용

동시 실행은 같은 구독 한도를 한꺼번에 쓴다. 한도가 빠듯한 세션에서는 3개가 동시에 실패할 수 있다 — 그 경우 실패한 축만 다시 띄운다.

## 강제

`hooks/review_nudge.sh`가 Agent 호출을 본다 — 리뷰어가 한 메시지에 하나만 떴을 때 "나머지 축도 같이 띄워라"를 알려 주는 것까지 확장할 수 있다(이번 변경에는 포함하지 않음 — 재검토 조건).

## 재검토 조건

- 도입 뒤 `/retro-fe`에서 리뷰 축이 직렬로 뜬 change 2회 → `review_nudge.sh` 확장.
- 동시 실행으로 한도 실패 3회 → 2+1로 나눠 띄우기.
