# ADR 0034 — 테스트는 시나리오를 덮는 최소가 기본값이고, 첫 push는 리뷰 뒤다

- 상태: 제안 (2026-09-20)
- 관련: adr/0018(red 게이트), adr/0027(위임·테스트 동결), adr/0031(산문 규칙은 기계로), care-app 2026-09-04~09-20 실측(세션 114개 · PR 33건 · 테스트 106파일)

## 문제

care-app에서 develop-fe(오버레이 develop-fe-simsimee)로 16일을 돌린 뒤 담당자의 체감은 "테스트가 엄청 많고 시간이 걸린다, 품질은 모르겠다"였다. 실측은 체감과 다른 곳을 가리켰다.

| 측정 | 값 | 뜻 |
|---|---|---|
| jest 666 테스트 / `verify` 전체 | 8초 / 27초 | **실행은 병목이 아니다** |
| 테스트 : 소스 줄 수 | 16,258 : 15,432 | 쓰는 양이 많다 |
| test 커밋 139개 중 새 파일을 만든 커밋 | 31개(22%) | 나머지는 기존 테스트 손보기 |
| test 커밋 중 재작업 | 42% | 리뷰 지적 한 줄 = `test(scope):` 커밋 + 위임 왕복 1회 |
| 케이스 중 배포되지 않는 목 어댑터 검증 | 17%(112건) | 사용자에게 닿지 않는 코드 |
| fix 커밋 표본 10건 중 이 계층이 못 잡는 종류 | 6건 | 실서버 계약 불일치 2 · 실기기 4 |
| Tier-2 PR당 커밋 중앙값 | 21개(상한 4~8) | 12건 전원 초과 |

규율은 지켜졌다 — 내부 모듈 mock 0건, skip·스냅샷 0건, testID 쿼리 7%, 동결 해제 0건. 즉 **"어떻게 쓰나"는 강제됐는데 "얼마나·어디에 쓰나"는 아무도 정하지 않았다.** workflow 3-2는 방법(실패 먼저·쿼리 우선순위·mock 경계)만 말하고, unit packet에는 분량 기준이 없다. worker는 시나리오 하나를 받으면 떠오르는 경계를 전부 쓴다 — 그게 성실해 보이기 때문이다.

커밋 수는 다른 원인이 겹친다. 테스트 분리 규칙(feat/fix에 테스트 혼입 금지)은 옳지만, 리뷰 루프 중에 push하면 그 뒤의 테스트 수정은 접을 수 없어 전부 독립 커밋으로 남는다. workflow 5장의 fixup은 "pre-push가 막았을 때의 대응"으로만 적혀 있다.

## 결정

### 1. 테스트 예산 — packet에 네 줄
workflow 3-2에 예산 조항을 두고, 테스트 unit packet에 그대로 넣는다.

1. 시나리오 1개 = 테스트 1개가 기본. 더 쓰려면 "어떤 다른 실패를 잡는가"를 리포트에 한 줄.
2. 배포되지 않는 코드(목 어댑터·픽스처·데모)는 계약 불변식(멱등·정렬·검증)만.
3. 린트가 이미 보는 것(토큰 클래스·스타일 값)·항등·존재 확인만 하는 렌더는 쓰지 않는다.
4. 헬퍼는 공용 fixture에서 import. 외부 응답은 손으로 쓴 가짜보다 실제 응답 픽스처 우선.

### 2. 첫 push는 리뷰 루프가 끝난 뒤
리뷰 반영으로 생긴 수정은 push 전에 fixup → autosquash로 원 커밋에 접는다. push 뒤(CI·사람 리뷰 조치)는 접지 않고 커밋을 더한다 — 강제 push 없이 지킬 수 있는 선이 여기다.

### 3. 수동 계약 프로젝트는 실제 응답 픽스처를 둔다
`docs/guides/api-contract.md` §7 ④. 못 잡은 6건 중 2건은 계층 문제가 아니라 입력 문제였다 — 테스트가 서버의 실제 응답을 한 번도 본 적이 없었다.

### 4. 재검토 조건 둘을 7장에 추가
fix 표본의 과반이 이 계층이 못 잡는 종류 → 테스트를 더 쓰지 말고 계층 보강. test 커밋 재작업 40% 초과 → 예산·fixup 점검.

## 버린 대안

- **커버리지 임계값**: 더 쓰게 만드는 장치다. 문제는 부족이 아니라 배분이다(도달률은 이미 94%).
- **테스트 분리 규칙 폐지**: 재작업 커밋은 줄지만 변조 방지(테스트를 초록에 맞춰 고치는 것)를 잃는다. 동결 해제 0건은 이 규칙이 작동한다는 증거다.
- **케이스 수 상한을 린트로**: 시나리오 수와 케이스 수를 기계로 대응시킬 수단이 아직 없다. 지금은 packet + retro 측정으로 두고, 재검토 조건이 발동하면 내린다.

## 비용

- 예산 ①의 "한 줄 사유"는 worker 리포트가 길어진다. 경계가 많은 순수 함수(날짜·파서)는 사유를 달고 더 쓰면 된다 — 금지가 아니라 기본값이다.
- push를 늦추면 작업 중 원격 백업이 없다. 로컬 커밋은 그대로 하므로 잃는 것은 디스크 장애 대비뿐이다. 팀 규약이 "중간 push 자유"여도 하지 않을 자유는 있다.

## 강제

- packet 네 줄: **사람 — 리뷰 2축**(산문이다. adr/0031에 비추면 약하다 — 아래 재검토 조건이 그 빚을 센다).
- 커밋 수: `templates/git-hooks/pre-push` 2-c 경고 + `templates/scripts/check-commits.sh`(adr/0036).
- 재작업 비율·fix 분류: `/retro-fe` 집계.

## 재검토 조건

- 예산 도입 뒤 티켓 3건에서 재작업 비율이 25% 밑으로 안 내려감 → 산문 강제의 한계다. 시나리오 ID ↔ 테스트 이름 대응을 기계로 세는 프로브를 만든다.
- 예산 때문에 놓친 회귀(있었어야 할 테스트가 "한 줄 사유" 부담으로 안 쓰임) 2회 → ①을 "시나리오당 1~2개"로 완화.
